# docs

The docs live in `docs/` (Docusaurus 3.10) and are built, not merely written. Three
facts they need are **read from the repo rather than restated**, because a second copy
is the one that goes stale — and it goes stale in the flattering direction, still
claiming a feature works months after it stopped:

| Fact | Read from | Rendered by |
| --- | --- | --- |
| Is this surface done, partial or planned? | `API.md` status table | `<Status of="signal" />` |
| The guard scripts, the pipeline, the shared tables | `architecture/data.ts` | `<Guards/>`, `<Pipeline/>`, `<TableRoles/>` |
| Does `signal.ts:140` still point at anything? | the tree, via `scripts/lib/citations.ts` | the remark plugin, at build time |

Do not hand-write any of those into a page. `<Status of="…" />` with a name that is
not in `API.md` is a build error, and that is the feature: you cannot document a
surface the tracking table has never heard of.

**The Internals pages inherit `arch:check`.** `<Pipeline/>` and `<TableRoles/>` render
`architecture/data.ts`, so a red `bun run arch:check` means those pages are rendering
stale claims — and nothing in `docs-check` will notice, because the citations live in a
`.ts` file rather than in Markdown. On 2026-08-02 that file still cited `app/app.tsx`
months after the directory became `windows/`. Run `arch:check` before trusting an
Internals page, and `arch:check --emit` after fixing it.

```bash
bun run docs               # dev server, citations warn instead of failing
bun run docs-check         # examples typecheck + API coverage + frontmatter
bun run docs-check --examples --keep   # just the examples, left on disk to inspect
bun run docs:build         # doc-lint + docs-check + the real build. The gate.
```

## The tools, and what each one proves

**`bun run docs-check`** — three checks, and the first is the one that matters.

*Examples compile.* Every ` ```ts ` and ` ```tsx ` block is extracted, given an import
of the authoring surface, and typechecked under **the repo's own tsconfig** — same
strictness, same `jsxImportSource`. So an example is held to exactly what a reader's
project would hold it to. Rename an export and the docs fail in the same run as the
code, not six weeks later in someone's terminal.

A fragment that cannot stand alone — one importing a project's own `./state.ts` —
gets ` ```tsx no-check `. Those are **counted and reported**, never silently skipped:
an unchecked example is a risk, and the number of them is the thing worth watching.
If that count is climbing, the examples are drifting toward decoration.

*The public surface is covered.* `src/index.ts` is where the public-versus-internal
line is drawn, so it defines what the docs owe a reader. The check runs both ways —
an export no page mentions is an undocumented feature; a page teaching
`import { foo } from "dziry"` when `foo` is not exported is a **phantom import**, and
that one fails hard because it is a lie a reader will act on.

*Frontmatter is present.* The sidebars are autogenerated, so a page missing
`sidebar_position` sorts arbitrarily and one missing `title` gets a name guessed from
its filename. Both fail quietly, which is the worst way to fail.

**`bun run doc-lint`** — citations across every Markdown file in the tree. The docs
site enforces the same rule at build time through the same resolver, so a rotted
`file.ts:LINE` inside `docs/` fails `docs:build` too.

## Writing a page

- **Document what is done.** Check `API.md` first. A planned surface gets a
  `<Status of="…" />` badge and, if it needs prose at all, a `:::warning` — not
  present-tense description of behaviour that does not exist.
- **Cite by line** — `src/runtime/signal.ts:140` — the same habit as the rest of the
  repo. It resolves at build time and links to the source when `DZIRY_SOURCE_URL` is
  set.
- **Prefer an example that compiles** over one that reads well. If it needs
  `no-check`, ask whether a smaller standalone version would teach the same thing.
- **Explain the constraint, not just the rule.** Nearly every restriction in dziry is
  one rule — *anything the runtime reaches by name must have a name at build time*.
  A reader who has that can derive the rest; one who has five memorised rules cannot.
- **Frontmatter**: `title` and `sidebar_position` on every page.
- Pages using components must be `.mdx`. Plain `.md` is CommonMark and will render
  `<Status/>` as literal text.

## If you change `docs-check`, make it fail first

The example checker shells out to `tsc`, and its natural failure mode is a **silent
pass**: a config error produces output with no per-file diagnostic, nothing matches
the parser, and the run reports that every example compiles while having checked
none of them. That happened on 2026-08-02 — two bugs stacked (the extraction
directory sat inside the `docs` workspace, so `import … from "dziry"` could not
resolve; and `include: ["."]` found no inputs) and it cheerfully printed
*all 25 compile*.

There is now a guard: unparseable `tsc` output is a hard failure. Do not remove it,
and when touching that code, prove the check can still fail before trusting that it
passes —

```bash
printf '\n```ts\nconst n: number = "no";\n```\n' >> docs/docs/api/signals.mdx
bun run docs-check     # must report the error, at that file and line
git checkout docs/docs/api/signals.mdx
```

A green checker nobody has seen fail is not evidence.

## What none of this can check

**Whether the prose is true.** Every check here is mechanical: the citation resolves,
the example compiles, the name is exported. None of them read the sentence.

That is not a hypothetical gap. On 2026-07-31 a cited comment in this repo turned out
to state the *opposite* of what the doc claimed, and an API design was built on it
before anyone opened the file. `doc-lint` was green the whole time, because the line
number was fine.

So a clean `docs-check` means "nothing dangling and nothing that fails to compile". It
does not mean the docs are right. When you change behaviour, **read the page**, not
just the checker.

## After a refactor

The order that wastes least time:

1. `bun run docs-check` — phantom imports and broken examples surface immediately.
2. `bun run doc-lint` — citations that moved.
3. Read the pages the change touched. Step 3 is the one that finds the real damage,
   and it is the one there is no tool for.

## Versioning

Docusaurus versioning is set up but unused — there is no released version yet.
`bun run docs:version 0.1` snapshots `docs/docs` into a version folder when there is
something to freeze. Do not run it before a release: an unnecessary snapshot doubles
every future edit.
